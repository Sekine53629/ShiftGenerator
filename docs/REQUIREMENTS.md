## 1. 目的

薬局のシフト表を Google スプレッドシート上で自動作成する。
Excel VBA 版 `Auto_Shift_Generator` の置き換え。

**できあがるシフト表の見た目と中身は、いまの Excel 版と同じ。**
違うのは作る手段だけ。

## 2. 完成形

### 2.1 Excel は経路に入らない

日々の運用で Excel を開くことはない。スプレッドシートだけで完結する。

移行のときに一度だけ実物を参照することはありうるが、**恒常的な依存にはしない**。
現在ある `tools/ExportFormatProfile.bas`（Excel から書式を書き出す VBA）は
この方針に照らすと位置づけが下がる。★1

### 2.2 出力（決定）

| | 中身 | 用途 |
|---|---|---|
| 作業用 | 1つのブックに月ごとのシート | データの置き場。Web アプリが読み書きする |
| 配布用 | **別ブックとして出力** | スタッフに渡す |
| 印刷用 | **PDF** | 貼り出す。優先度は低い |

**作業用を別ブックに分けられない理由がある。**
集計の数式が `自動作成設定` シート（区分・必要出勤数）と `祝日マスタ` を参照している。
月ごとに別ブックにすると、これらが `IMPORTRANGE` になり、
承認が要るうえ再計算が遅く、壊れやすい。

そのため **作業は1つのブックの中で行い、固まったら別ブックへ書き出す**のが素直。
これは VBA 版の `ShiftExport` が「値と書式を固めた別ブックを作って印刷する」と
していたのと同じ発想。

### 2.3 月次の流れ（想定）

```
1. 新しい月のシートを作る          … シートを生成（書式・数式込み）
2. 希望休・有休を入れる            … 手入力
3. 自動作成を実行                  … 空白を埋める
4. レポートを見て手直し            … 過不足・連勤・ノルマ未達を確認
5. 配布用に書き出す                … 別ブック + PDF          ★2
```

## 3. 書式をどう決めるか（決定）★1

**書式プロファイルは移行用の道具ではなく、恒久的に残る資産。**

セルの大きさとテキストが確定していれば、同じデータで
**HTML でも描けるし、スプレッドシートの書式としても当てられる**。
Web アプリのグリッドと印刷物の見た目を揃える元になる。

```
              書式プロファイル（スクリプトプロパティ）
             ／                              ＼
   Web アプリの HTML                  スプレッドシートの書式
   （画面で見る）                      （印刷・配布物）
```

したがって:

- **プロファイルの仕組みは残す**（両方のレンダラが共有する）
- Excel エクスポータ（`tools/ExportFormatProfile.bas`）は
  **最初に埋める手段の1つ**。移行が済んだら `archive/` へ移してよいが急がない
- Web アプリ側にプロファイルを渡す実装は**エンジンの後**

### 旧: 書式をどう決めるか（経緯）

「スプレッドシートのフォーマット書式に入れる形」という言葉の解釈が2通りある。

| | 内容 | 影響 |
|---|---|---|
| **A. Sheets 側で定義し直す** | 見本となる書式を Sheets 上で1つ作り込み、それを正とする | `FormatProfile` の取り込み機能と Excel エクスポータは不要。既定値を作り込むだけ |
| **B. 実物から測って持ってくる** | いまの Excel の見た目を数値として持ち、再現する | いま作ったものが活きる。ただし Excel への一度きりの依存が残る |

**私の見立ては A。** 恒常的に Excel を開かないなら、書式の正は Sheets 側にあるべきで、
「Excel から測る」機構は移行が済んだ時点で死ぬ。
既定値（`Config.gs` の `FORMAT_DEFAULT`）を実物に合わせて詰めれば足りる。

A を採る場合、次のものは役目を終える。

- `tools/ExportFormatProfile.bas`（Excel エクスポータ）
- `FormatProfile.captureFormatProfile` / `importFormatProfileJson`（取り込み）
- `ImportProfileView.html`

**書式プロファイルの仕組み自体（役割ごとに色や高さを持ち、生成時に当てる）は
どちらでも残る。**変わるのは「値をどこから得るか」だけ。

## 4. スコープ

### 入るもの

| 機能 | 状態 |
|---|---|
| シフト表シートの生成（書式・数式込み） | 実装済み |
| 不足シートの生成（設定・祝日・ログ） | 実装済み |
| 祝日マスタの取込 | 実装済み |
| 位置解決・ログ | 実装済み |
| **配置アルゴリズム（自動作成）** | **未着手（71 関数）** |
| 結果レポート | 未着手 |
| 設定チェック・事前診断 | 未着手 |
| 変更ログとセッション単位の巻き戻し | 未着手 |
| 配布用ブックの書き出し + PDF | 未着手 ★2 |

### 入らないもの（仕様書 §1 のとおり）

シート上のパレット3行 / ダブルクリックの順送り / 右クリック /
和暦の表示形式 / スピンボタン / Excel(.xlsx) 出力 / `Erl`

### 4.5 Web アプリが主役（決定）★3

Web アプリはスプレッドシートの補助ではなく、**この道具の本体**。

| 担うこと |
|---|
| 希望休の取り込み |
| 医師出勤日の取り込み |
| 予測モデルの実行 |
| それに合わせた出勤パターンの最適化 |
| 出力（配布用ブック / PDF） |

**スプレッドシートは「データの置き場と配布物」に降格する。**

### 4.6 シートに数式を持たせない（決定）★

Web アプリが計算するので、シート側に数式は要らない。集計は**値として書く**。

これで仕様書 §5（数式の移植）のほぼ全部が不要になる。

| 消えるもの | |
|---|---|
| §5.3 `MATCH` に配列を渡せない問題 | **丸ごと消える。**区分の作業列 `AN` も不要 |
| §5.4 集計行・集計列の数式 | Web アプリが計算した値を書く |
| §5.5 名前付き範囲 | 位置を自前で持つなら不要 |
| 祝日サマリーの数式 | 同上 |
| `Setup.gs` | **不要**（★4 解決） |

**「エラーにならず黙って誤った人数を返す」という移植で最も危ない箇所が、
設計ごと消える。**

#### ただし1つ壊れる ★8

**`Layout` の日付行の判定が成り立たなくなる。**
いまは「B列で数式かつ日付のセル」を目印にしているので、数式が無ければ必ず失敗する。

実際に「シフト表として読めませんでした」で詰まったのは、これと同じ問題だった。

代わりの方式が要るが、**むしろ簡単になる**。シートを生成するのは自分なので、
位置を推測する必要がない。**推測をやめるのが本質。**

| | |
|---|---|
| A. 固定位置 | 生成時に決めた行を定数で持つ |
| B. シートごとに記録 | ドキュメントプロパティに「シート名 → 位置」を持つ |

B なら行の増減に追随できる。

#### 決めが要る ★9

**Web アプリが唯一の書き手か。**
数式を捨てると集計は静的な値になるので、シートを直接編集されると集計が古いまま残る。
「直接編集は想定しない」と決めておく必要がある。

## 5. どこを忠実に移し、どこは変えてよいか（確定）

**Excel から移したいのは「見た目」。人工計算のロジックには改良の余地がある。**
この2つを混ぜないこと。

| 対象 | 方針 |
|---|---|
| **シフト表の見た目**（色・寸法・行構成・集計の並び） | **忠実に移す** |
| **配置アルゴリズム**（誰をどの日に置くか） | **VBA と同じ出力**。仕様書 §4 のとおり |
| **必要人数の算出**（`required` の作り方） | **改良してよい**。いまは `医師数 + n` の固定式 |

3つ目が変えられるのは、エンジンが `days[].required` しか見ないため。
これを作っているのは `ShiftAuto.buildDayInfo_()` の1関数だけで、
**エンジンには手を入れずに差し替えられる**。

ただし順序がある。`required` を変えると「同じ入力なら同じ出力」の検証が
定義上できなくなるので、**移植の突き合わせが済むまでは固定式のまま**にする。
改良の構想は [`DEMAND-FORECAST-CONCEPT.md`](DEMAND-FORECAST-CONCEPT.md) に分けた。

### 配置アルゴリズムの厳密さ

**VBA 版と同じ出力**。仕様書 §4 と §9 フェーズ3 のとおり。

これは次を意味する。

- 検証のために **VBA 版で実データ（匿名化）を流し、`mPlan` / `mSymb` を吸い出す作業**が要る
- 移植中にアルゴリズムを「改善」しない。不満があっても移植後に別の変更として行う
- `Engine.gs` は `SpreadsheetApp` を呼ばない純粋関数のままにする

**すでに1か所、VBA 版と結果が変わる変更を入れている。**
`WORK_SYM_PREFIX_MATCH`（派遣行の「▲＋氏名」を出勤として数える）。
検証のときは `false` に戻して比べること。
`CB_CHAIN_MAX_PASS`（玉突きの打ち切り）も VBA 版に無い制限。

## 5.4 月をまたぐ連勤・連休（決定）

シフトは月ごとに作るので、**前の月の末尾で何があったかを知らないまま**
新しい月の1日目を置いている。第1週の後半4日 + 第2週の前半4日で8連勤、
のような形が月境で起きる。

### 週を割っても解決しない

「週を半分に割って管理する」案が出たが、**前月の情報が無いので防げない**。
割り方をどう工夫しても、前月に何があったかは知りようがない。

### 週N日は実は安全

按分は必ず正しく合計される。

```
週の目標 = Int(週N日 × その月にある日数 / 7 + 0.5)

8/30-31 が2日 → Int(4×2/7+0.5) = 1
9/1-5  が5日 → Int(4×5/7+0.5) = 3
                        合計 = 4  ✓
```

どの割れ方でも合う。`週N日 × 日数 / 7` がちょうど 0.5 刻みになることが
ありえないため（`2ax = 7(2k+1)` は左辺が偶数・右辺が奇数で不成立）、
両方が切り上がって1日多くなる事故が起きない。

**したがって問題は連勤・連休だけ。**

### 前月の末尾を持ち越す（実装済み）

前月の**末尾7日ぶん**を、月外だが「既存入力」として渡す。
連勤上限3・連休上限3なら、それ以上遡っても判定は変わらない。

日に `locked: true` を立てると、エンジンは次のように扱う。

| | |
|---|---|
| 配置する工程 | `ST_WORK` しか触らないので**自動的に避ける** |
| `runLenAt_` / `offRunBefore_` / `offRunAfter_` | 月内かを見ずに走査するので**連勤が正しく繋がる** |
| 公休ノルマの母数・週リスト・混雑日 | `dayIn` で絞っているので**持ち越しは数えない** |

**持ち越しを渡さなければ、これまでと完全に同じ挙動になる。**
移植の突き合わせを壊さない。

残るのは `ShiftAuto` 側で前月のシートを読む実装（未着手）。
前月のシートが無ければ持ち越し無しで動く。

## 5.5 個人の戦力は点数にしない（確定）

人によって処理できる量は違う（派遣薬剤師は調剤はできるが締め作業はできない、など）。
技術的には重み付けできるが、**やらない。**

1. **点数は現場の反感を買う。**共有シートに「この人は 0.6」と並ぶのは人事評価が
   表に出ているのと同じ。既存の `遅番・遅半 可否` が受け入れられているのは、
   あれが**事情**に読めるから。点数は**評価**にしか読めない
2. **隠すと説明できなくなる。**数値で持つと、隠すか説明するかのどちらかを諦めることになる
3. **保守が実利を上回る。**6人 × 3指標を、根拠になるデータ無しに誰かが保守することになる

**指針: 能力は「条件」の形で表し、「点数」の形にしない。**

代わりにフラグで表す。理由の詳細は
[`DEMAND-FORECAST-CONCEPT.md`](DEMAND-FORECAST-CONCEPT.md) §7。

| 表したいこと | やり方 |
|---|---|
| 調剤ができない | `区分` を分ける（既存の仕組み） |
| 締め作業ができない | `締め作業 可否` の欄を足す ★6 |
| どのくらい速いか | **表さない** |

この判断により、**重み付き `cov` とそれに伴う `CoverBalance` の式の作り直しが不要**になった。
エンジンの中核に手を入れずに済み、移植の検証も壊さない。

## 5.6 クリニックの休診日（決定）★7

クリニックは年中無休。**年末年始 12/29〜1/3 の6日だけが休診**。
日付は決め打ちしてよい。

### 公休ノルマの母数に加える

休診日は**祝日と同じ扱い**にする。ノルマを増やし、同時に消費するので、
**他の日の休みは変わらない**。

```
いま       : ノルマ = 土日 + 平日の祝日
休診を足す : ノルマ = 土日 + 平日の祝日 + 平日の休診日
```

### 実装（エンジンには手を入れない）

| | |
|---|---|
| 1 | 休診日を `Config.gs` に決め打ち（12/29〜1/3） |
| 2 | `importHolidays` が `祝日マスタ` に休診日の行も書く。名称は `年末年始休診` |
| 3 | `SheetBuilder` が休診日の列に全員ぶん `公休` を入れて生成する |

2 は**決め打ちなので取り込みのたびに再生成できる**。
手で足した行が消える、という問題が起きない。

3 により、休診日は既存入力（`ST_FOFF`）としてエンジンに渡る。
エンジンは触らず、`公休` はノルマ対象なので増えた母数をちょうど消費する。

### 二重計上は起きない

休診日が土日に当たっても、祝日サマリーの数式は `WEEKDAY(d,2)<6` で
**平日だけを数えている**ので重複しない。

### 文言

サマリーの文言を **「祝日」→「祝日・休診」** に変える。
中身が「祝日1 + 休診2」でも「祝日3回」と出てしまうため。

### 空欄の多義性は別途決めが要る

医師数セルの空欄が「未入力」と「休診（0診）」の2つの意味を持つ点は残る。
ただし休診日が決め打ちになったので、**当面この6日以外に休診は無い**。
優先度は下がった。

## 7.5 導入（職場環境）

開発は自宅の個人アカウントで行っている。職場へ移すのは
`.clasp.json` の差し替えとシートの用意だけ——**技術的には**。
実際のネックは職場側の環境で、こちらからは見えない。

### 道具が完成する前に確かめること

完成してから「職場では動きません」と分かるのが最悪。先に確認する。

| # | 確認 | 詰まったときの意味 |
|---|---|---|
| 1 | 拡張機能 → Apps Script が出るか | 出なければ組織が禁止。打つ手がない |
| 2 | Apps Script API をオンにできるか | できなければ `clasp` が使えず**20ファイル手貼り** |
| 3 | 関数を実行して承認画面が出るか | 「管理者によりブロック」なら管理者対応が要る |
| 4 | ウェブアプリの公開範囲に何が選べるか | 組織ポリシーで絞られていることがある |
| 5 | `UrlFetchApp` が外部へ通るか | 通らなければ祝日は手入力 |

**2 が塞がっているケースが最も多い。**

### 移行時に決めること

- **スプレッドシートの所有者。**個人アカウントのままだと、退職・アカウント停止で
  シフト表ごと消える
- **自宅の練習用ブックに入れた実データの扱い。**消すのか、匿名化して残すのか

前者は業務継続、後者は個人情報の話。

## 8. 決まったあとの進め方（案）

1. ★8（`Layout` の位置解決）を決める — **実装の前に要る**
2. 要らなくなったものを片付ける（`Setup.gs`、数式生成、作業列 `AN`）
