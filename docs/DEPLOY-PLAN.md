# 運用とデプロイの設計

決めたこと（2026-09-06）:

- 構成は **B** — プロトタイプの HTML を Web アプリの画面にし、保存先だけ Sheets にする
- 展開は **6店舗**、今後増える前提
- **アカウントを持たない職員がいる**

この3つ目が設計を決める。以下はそこから逆算した形。

---

## 1. 全員にアカウントを配らない

編集する人と、見るだけの人を分ける。**編集する人だけアカウントが要る。**

| 役割 | 人数の目安 | やること | 経路 | アカウント |
|---|---|---|---|---|
| 本部 | 数名 | 全店のマスタとシフト | Web アプリ | **必要** |
| 店舗マネージャー・管理薬剤師 | 店あたり1〜2名 | 自店のシフト作成・編集 | Web アプリ | **必要** |
| 一般職員 | 大多数 | 自分のシフトを見る | **PDF 配布** | 不要 |

6店舗なら編集者は **15アカウント程度**。この規模なら Workspace でも個人 Gmail でも回る。

### 一般職員の閲覧を Web にしない理由

いまは紙か PDF が配られている。同じものを Web で出すと、**掲示板より露出が広がる**。
URL は転送できるが、休憩室の紙は転送できない。実名と勤務が入っているので、
ここは意識して決める必要がある。

第1段階では **入れない**。PDF の配布で足りる（命名則は実装済み、§4）。

将来どうしても入れるなら、次の形になる。今は作らない。

- 店舗×月ごとに、失効できるランダムなトークンを発行する
- Web アプリを「全員（匿名を含む）」でデプロイし、`doGet` でトークンを検証する
- トークンに紐づく1か月ぶんの表だけを返す。マスタも他店も返さない
- 漏れたら発行し直す。**紙より露出が広いことを承知のうえで入れる**

---

## 2. デプロイは1つ。各店には配らない

**スクリプトは1つ、Web アプリのデプロイも1回、URL も1つ。**

```
  実行するユーザー   … アクセスしているユーザー
  アクセスできる人   … Workspace があれば「組織内の全員」
                       無ければ「Google アカウントを持つ全員」
```

後者は組織外の人も URL に到達できるので、`doGet` で
`Session.getActiveUser().getEmail()` を社員マスタと突き合わせ、**登録が無ければ弾く**。
弾いた事実は実行ログに残す。

### 各店デプロイにしない理由

1. **BI と予測が成立しなくなる。** 店舗横断の比較（`docs/DEMAND-FORECAST-CONCEPT.md`）は
   データが1か所に無いと組めない
2. **VBA 時代の問題に戻る。** 全店にコピーして回る運用がつらかったからこの移植が始まった
3. 更新が1回で済む。`clasp push` → デプロイを更新 → URL は変わらない

### 版の見分け

`CONFIG.APP_VERSION` を画面に出す仕組みは既にある。**コードを変えたら必ず上げる。**
Web アプリはデプロイ時点の版を動かし続けるので、これが無いと
「直したのに反映されない」の切り分けが付かない。

---

## 3. データの置き場所

**Apps Script に本物のデータベースは無い。**永続する置き場は3つだけ。

| | 容量 | 向き |
|---|---|---|
| PropertiesService | 1値 9KB・全体 500KB | 設定値どまり。マスタには小さい |
| CacheService | 最大6時間で消える | 保存には使えない |
| **Drive のファイル** | 実質無制限 | **JSON 1個をそのまま置ける** |

マスタは入れ子の構造（社員が使える記号の配列、店舗ごとの営業時間…）なので、
セルの表に展開すると項目を足すたびに列対応を書き直すことになる。
JSON のまま置けば、画面が持つ形をそのまま保存できる。**保存は Drive のファイル。**

```
  AutoShiftGenerator データ（Drive のフォルダ／ID はスクリプトプロパティ）
    ├─ masters.json                 マスタ。全店で1つ
    ├─ cells-<店舗>-<yyyy-mm>.json  シフト。店舗×月で1ファイル
    └─ …

  シフト管理スプレッドシート
    ├─ 出力したシフト表             Export.gs が挿す。人が読む表はこちら
    └─ 実行ログ

  レセコン明細スプレッドシート（別）
    └─ 日次データ        行が増え続けるので分ける
```

**月ごとにファイルを分けることが、同時編集の単位になる。**1ファイルに
まとめると、別の店・別の月を触っただけで衝突する。

### 同時編集は「検知して知らせる」

ファイルごとに版番号（rev）を持つ。画面は読んだときの rev を覚えておき、
保存のときに一緒に送る。サーバは今の rev と突き合わせ、**違っていたら書かない。**

```
  A さんが読む（rev 3）
  B さんが読む（rev 3）
  A さんが保存           → rev 4
  B さんが保存（rev 3）  → 書かない。今の中身と「誰がいつ書いたか」を返す
                           画面は「読み直す」か「自分の内容で保存」を出す
```

誰かの編集を黙って消すより、画面に出して選ばせる。セル単位の自動マージは
採らない。自動生成は表全体を書き換えるので、結局どこかで衝突する。

読んで・比べて・書くの間に割り込まれないよう、`LockService` で囲う（最大20秒待つ）。

ほかの人の保存は30秒ごとに見に行く。**こちらに保存待ちがあるときは取り込まない。**
入力中に上書きすると、打っている途中の内容が消える。

1店1年ぶんのシフトは約 4,400 セル。**30店・3年でも 40万セル**だが、
JSON なら1か月ぶんで数十 KB にしかならない。

明細を分けるのは、レセコンの日次データが行数で伸びるため。

## 4. 構成 B で、何が要らなくなるか

配置エンジンはブラウザで動かす。GAS 側は読み書きと認証だけを持つ。

```
  いまの未実装      構成Bでの扱い
  Engine.gs    37   不要（ブラウザ側に移る）
  ShiftAuto.gs  1   不要（自動生成の入口はブラウザ）
  Report.gs     6   後回し（第3段）
  Intake.gs     5   後回し（第4段）
  ChangeLog.gs  8   要る
  Setup.gs      7   要る
  Export.gs     3   要る（PDF）
  SettingsCheck 2   要る
  Survey.gs     9   要る（Excel からの移行。様式が3種ある）
  Log.gs        1   要る
```

**81 → 30 に減る。**うち第1段で要るのは ChangeLog / Setup / SettingsCheck / Log の 18 と、
Web アプリの保存 API。

6分制限も構造的に回避できる。重い計算がサーバに来ない。

### 弱点

**サーバ側の定期実行ができない。** 「毎月1日に翌月分を自動生成してメールで知らせる」
といったバッチは、この構成では組めない（ブラウザを開かないと動かない）。
いまその要件が無いので採る。要るようになったら、そのときだけ
エンジンを .gs に移す判断をする。

## 5. 段階

| 段 | 内容 | 判断の材料 |
|---|---|---|
| **1** | 1店（基準店）で Web アプリ化。保存先を Sheets に。編集者2名 | 実運用で1か月まわるか |
| **2** | 6店へ展開。権限3段階、店舗切替 | 店舗横断で壊れないか |
| **3** | PDF 出力の自動化と配布 | 手作業がどれだけ減るか |
| **4** | レセコン取り込み、BI・予測 | 処方箋枚数が取れているか |

第1段は**いまの基準店のデータをそのまま入れて、1か月ぶんを実際に作る**のが検証になる。
13か月ぶんの実績と突き合わせられる。

## 6. 仕様書との食い違い

Tier 3 の `CLAUDE.md` と仕様書 §9 は「VBA と同じ出力になる移植」を前提にしている。
**その前提はもう成り立っていない。**

2026-09 の作業で、実データを根拠に VBA には無い決定を入れた。

- 週次で出勤日数を管理する
- 公休はノルマちょうど（超過分は有休・夏休）
- 曜日別下限は使わない。必要人数は診療数で決める
- 連続出勤の上限は既定4日
- 医師名欄の行数を可変にする

いずれも `docs/REAL-SHIFT-ANALYSIS.md` に根拠がある。移植ではなく作り直しなので、
**「完成」の定義を書き換える必要がある。** 検証の基準は
「VBA と同じ出力か」ではなく「13か月の実績と整合するか」になる。
