# レセコン連携の受け口

レセコン（シグマ）から日次の実績を受け取るための **こちら側の仕様**。

ベンダーとの交渉は「何が出せますか」から始めると話が発散する。
**こちらが受け取れる形を先に決めておけば、「この形に寄せられますか」で済む。**
実装より先にこの契約を固める。

> 何を溜めるかは [FEATURE-COLLECTION.md](FEATURE-COLLECTION.md) を参照。

---

## 1. 受け取る形（正規形）

**ベンダーに依存しない形をこちらで定義し、変換はアダプタが担う。**
シグマの出力形式がどうであれ、この形に直してから中へ入れる。
将来レセコンを替えても、アダプタを差し替えるだけで済む。

```json
{
  "source": "sigma",
  "fetchedAt": "2026-10-02T09:15:00+09:00",
  "records": [
    {
      "storeCode": "STORE-01",
      "date": "2026-10-01",
      "counts": {
        "prescriptions": 118,
        "newPatients": 9,
        "onePack": 12,
        "mixing": 4,
        "compounding": 2,
        "duplicationCheck": 3,
        "narcotics": 1,
        "homeVisit": 2,
        "internalDrugUnits": 214
      },
      "dispenseDays": { "7": 12, "14": 30, "28": 41, "30": 18, "56": 9, "90": 8 },
      "patients": [
        { "patientNo": 12345,  "days": 28 },
        { "patientNo": "A-0007", "days": 90 }
      ],
      "byDoctor": [
        { "doctorCode": "DR001", "prescriptions": 34 },
        { "doctorCode": "DR002", "prescriptions": 28 }
      ]
    }
  ]
}
```

### 項目の定義

**加算の数え方は算定ルールで既に決まっている。** ベンダーと合意する話ではない。
ただし**加算ごとに単位が違い、作業量への比例のしかたも違う**ので、そこを取り違えると
特徴量として使えない。

| キー | 内容 | 数え方 | 作業量との関係 |
|---|---|---|---|
| `prescriptions` | 処方箋の枚数 | 枚 | 基本の量 |
| `onePack` | 一包化加算 | **1処方箋につき1回** | **比例しない**。下記参照 |
| `onePackDays` | 一包化した処方の投与日数（合計） | 日 | **一包化の工数はここに出る** |
| `mixing` | 計量混合調剤加算 | **混合の回数だけ** | 比例する |
| `compounding` | 自家製剤加算 | **1処方に複数取れる**（剤ごと） | 比例する |
| `duplicationCheck` | 重複投薬・相互作用等防止加算 | 算定回数 | 照会1件ぶん。**疑義照会の下限値** |
| `narcotics` | 麻薬管理指導加算 | 算定回数 | |
| `homeVisit` | 在宅患者訪問薬剤管理指導料 | 算定回数 | |
| `internalDrugUnits` | 内服薬の剤数（合計） | 剤 | 調剤料の算定根拠。手間にほぼ比例 |
| `newPatients` | 新患 | 人 | 「初来局」か「その保険での初回」か要確認 |
| `patients` | 患者ごとの（通し患者番号, 処方最大日数） | 行 | **次回来局日の予測はここからしか作れない**。番号は取り込みの境界でハッシュ化し、保存しない |
| `dispenseDays` | 処方日数 → 件数 | 件 | 患者台帳が取れないときの代替。残日数を追えない |
| `byDoctor` | 医師コード → 枚数 | 枚 | 医師マスタと突き合わせるコードが要る |

### 一包化だけ性質が違う

計量混合と自家製剤は**作業回数がそのまま件数**になるので、件数がそのまま工数に効く。
一包化は**1処方箋につき1回しか算定できない**ので、件数は「一包化した処方箋が何枚あったか」
にしかならない。**14日分の一包化と90日分の一包化が、同じ「1」になる。**

一包化の工数は**投与日数**で決まる。だから件数だけでなく、
`onePackDays`（一包化した処方の投与日数の合計）を併せて取る。
算定点数が投与日数の区分で変わる仕組みなら、**点数から日数を逆算してもよい**。

### 患者の個票 — 通し番号で受け取り、境界でハッシュ化する

次回来局日の予測には患者単位のデータが要る（残日数を追うため）。
**通し患者番号がクリニック側にも薬局側にもある**ので、キーには困らない。

ただし通し患者番号は**患者を特定できる番号**。薬局に対応表がある以上、
シートにそのまま置くと、持ち出された時点で氏名まで辿れる。
シートは共有・書き出し・控えの対象なので、そこには置かない。

**受け取りは `patientNo`（生の通し番号）で構わない。取り込みの境界で
ハッシュ化し、保存するのはハッシュだけにする。**

```
patientNo 12345  →  patientKey "e48b7a059ad0a16772b3765d"
```

| | |
|---|---|
| ソルト | スクリプトプロパティに置く。シートには出さない |
| なぜソルトが要るか | 患者番号の空間は小さい（数万程度）。ソルト無しのハッシュは総当たりですぐ逆引きできる |
| **ソルトは変えない** | 変えると過去の患者キーと突き合わせられず、残日数の追跡が切れる。**控えを取ること** |

**これが守るもの・守らないもの**

- 守る … シートが外へ出たときに、そこから患者を辿れないこと
- **守らない** … スクリプトを触れる人はソルトを読めるので、その人には無力。
  法令上の「匿名加工情報」にはならず、**取扱いは個人情報のまま**

**氏名・生年月日・保険証番号・住所が入っていたら、その行は取り込まない。**
黙って捨てると送る側は送り続けてしまうので、行ごと弾いて理由を返す。

```
次回来局予定 = 今回の来局日 + 今回の処方最大日数 + 前回の残日数
前回の残日数 = 前回(来局日 + 処方日数) − 今回の来局日     （負なら 0）
```

5日早く来た患者は手持ちが5日残るので、次回は予定どおり来た患者と同じ日になる。
**この持ち越しは集計値では表せない。**

### 加算名ではなく「作業の種類」でキーを持つ

診療報酬は改定で名称・区分・点数が変わる。**加算の名前をそのままキーにすると、
改定のたびに系列が切れる。** キーは「何の作業か」（一包化・混合・製剤・照会）で持ち、
どの加算に対応するかは対応表で持つ。

過去データを溜める目的からすると、これは効く。5年後に振り返るとき、
名前が3回変わっていても同じ系列として追える。

## 2. 受け口は3経路

どれか1つに賭けない。**シグマが API を出せない可能性が十分にある**ので、
CSV 経由でも同じ場所へ入る作りにしておく。

| 経路 | 使う場面 | 実装 |
|---|---|---|
| **A. CSV 手動アップロード** | まずこれ。API が無くても始められる | 画面からファイルを選ぶ |
| **B. Drive のフォルダ監視** | レセコン側が定時に CSV を吐ける場合 | 時間主導トリガで新着を拾う |
| **C. Web API（doPost）** | シグマが push できる場合 | `/exec` に POST |

**A から作る。** A が動けば、B は「ファイルの置き場が変わるだけ」、
C は「入口が HTTP になるだけ」で、変換と保存は共通。

## 3. 守ること

**冪等にする。** 同じ日を何度取り込んでも結果が変わらない。
`店舗ID × 日付` で upsert し、追記しない。レセコンの値はあとから確定するので、
再取り込みは日常的に起きる。

**出所と取得日時を必ず残す。** どの経路でいつ取った値かが分からないと、
食い違ったときに調べようがない。

**未知の項目を捨てない。** 契約に無いキーが来たら `extra` に丸ごと残す。
捨てると、あとで「その項目も欲しかった」となったとき遡れない。

**欠測と 0 を区別する。** 項目が来なかった日と、0件だった日は別物。
0 で埋めない。

**部分的に壊れたデータで全体を止めない。** 行単位で検証し、
通った行だけ入れて、弾いた行は理由付きで残す。

**認証は共有シークレット。** C を使うなら、`X-Api-Key` をスクリプトプロパティと
突き合わせる。GAS の Web アプリは URL を知られると誰でも叩けるので、
「リンクを知っている全員」で公開するなら必須。

## 4. シグマに確認すること

そのまま渡せるようにまとめてある。

**出せるかどうか**

1. 日次で出せるか。**出せなくても致命的ではない**（管理帳簿に項目を足して
   打ち込めば予測には使える）。ただし手入力の負担が続くかは別問題なので、
   自動で出せるならそのほうがよい
2. 出力形式は CSV か、API か。API ならプッシュ型かプル型か
3. 加算の算定回数を項目別に出せるか（一包化・計量混合・自家製剤・重複投薬相互作用等防止）
4. **患者ごとに（通し患者番号・来局日・処方最大日数）を出せるか。**
   次回来局日の予測はこれが要る。**番号のままで構わない**
   （こちらの取り込みでハッシュ化し、生の番号は保存しない）。
   氏名・生年月日は送らないでほしい
5. 上が無理なら、処方日数の分布（日数ごとの件数）は出せるか
6. 医師ごとの処方箋枚数を出せるか。医師を識別するコードは何か

**定義の確認**

7. **一包化について、投与日数（または算定点数）も出せるか。**
   件数だけでは工数が分からない（1処方箋につき1回しか算定できないため）
8. 処方箋枚数は受付回数か、処方箋の枚数か
9. 締めのタイミングはいつか。値はいつ確定するか。遡って変わることはあるか
10. 店舗を識別するコードは何か

**運用**

11. 追加費用と、対応にかかる期間
12. テスト用のサンプルデータをもらえるか（**これが早くもらえると開発が進む**）
