# 需要予測による人員配分 — 次期プロジェクトの構想案

2026-09-04 記録。**構想であって、着手の予定ではない。**

いまの移植（`GAS-PORTING-SPEC.md`）と要件（`REQUIREMENTS.md`）の範囲外。
本移植が終わったあとに、別の変更として検討する。

**置き場は決まった。**Web アプリが主役になり、その担うことの1つに
「予測モデルの実行」が入った（`REQUIREMENTS.md` §4.5）。
つまりこの構想の差込口は Web アプリの中にある。ただし**中身は段階のまま**で、
着手の予定は変わらない。

---

## 1. なぜ要るか

シフト作成は、**クリニックの診療体制が確定する前に着手することがある**。
いまの仕組みは医師数（`医師数(診)` 行）を必要人数の唯一の駆動因子にしているので、
医師数が未入力の日は必要人数が出せない。

```
必要数 = 医師数 + n        （n は 自動作成設定 L列「必要出勤数(医師数+n)の n」）
```

医師数が埋まるのを待たずに組めるようにしたい。

---

## 2. 医師数は「完全な指標」ではない ★前提

いまの仕組みは `必要数 = 医師数 + n` で、医師数を唯一の駆動因子にしている。
**これは粗い。**医師数と薬局の負荷は、片方がもう片方を生む関係ではない。

```
              患者需要（本体）
             ／            ＼
      医師出勤数            処方箋枚数
   （クリニックの体制）      （薬局の実負荷）
```

どちらも患者需要の下流にある。相関するのは共通の原因を持つからで、
**医師数は体制側の粗い信号にすぎない**。
5診でも空いている日はあるし、3診でも混む日はある。

医師出勤数はおおむね需要に追従しているが、
**完全な指標として扱うと、混む3診の日に人を減らすことになる。**

## 3. 何が寄与するか（現場の見立て）

需要は少なくとも4つの要素の重ね合わせ。それぞれ性質が違う。

### 3.1 定期患者の再来

最も強く、最も読める。処方箋に**処方日数と次回予約日**が書かれている。

- 予約は**7の倍数に寄る**（28日が特に多い。30日・32日もある）
- **処方日数 + 手持ちの残薬日数**で、より確かな来局日が出せる
- 過去の処方から未来の来局を積み上げる（畳み込み）

### 3.2 新患

再来の畳み込みでは出てこない。別の過程で発生する。
曜日と季節（流行期）のベースラインとして扱うことになる。

### 3.3 休日によるローリング ★見落としやすい

28日後が日曜・祝日なら、来局は前後にずれる。連休があればまとめてずれる。

- **ずれの向きはクリニックの運用次第**。連休前に前倒しするのか、
  明けに後ろ倒しになるのか、データを見ないと分からない
- 祝日が多い月は診療日が減り、**同じ患者数がより少ない日に圧縮される**。
  1日あたりの負荷は上がるのに、医師数は変わらないことがある
- ここは医師数からは読めない。**医師数を唯一の指標にすると必ず外す**

`祝日マスタ` は既にあり、**年末年始の休診日（12/29〜1/3）も同じシートに入る**
ことが決まった（`REQUIREMENTS.md` §5.6）。営業日カレンダーとしてそのまま使える。

### 3.4 診療体制（曜日）

曜日ごとに標準の診療体制が決まっている。これは予測ではなく**設定**（段階1）。

### 3.5 使わないと決めた要素 ★

**特徴量は「計画時点で分かるもの」に限る。**
シフトは数週間前に組む。その時点で値が手に入らないものは、
相関がどれだけ強くても特徴量にならない。

| 要素 | 計画時点で分かるか | 判断 |
|---|---|---|
| 処方日数・次回予約日 | ○ 過去の処方箋にある | 使う |
| 曜日・祝日 | ○ カレンダーで確定 | 使う |
| 医師数 | △ 確定していることもある | 使う（あれば優先） |
| **天候** | **×** 1か月先は分からない | **使わない** |
| **室温・湿度** | **×** 同上 | **使わない** |

**季節性は使える。**「2月は雪で多い／少ない」という平均的な傾向は
カレンダーから分かるので、天候が持っていた説明力の大半は季節性が吸収する。
天候そのものを取りにいく必要はない。

**日報の室温・湿度は外気の代理にならない。**
調剤室・冷所の管理値で、基準内に収めるよう空調で制御している。
測っているのは空調の設定に近い。**立入検査用の記録**として位置づけ、
需要データと混ぜない。

**大雪は別枠だが、予測の話ではない。**
雪の多い土地なので、大雪でスタッフが来られない日はある。
ただしそれは「来月のシフトを組む」ではなく「当日に差し替える」話で、
変更ログと巻き戻し（フェーズ5）の領域。

## 4. 段階

### 段階1: 曜日別の標準診療体制 ★これは予測ではない

「月曜は5診、日曜は3診」のような**標準体制を設定として持ち、
医師数が未入力の日をそれで埋める**だけ。

- 予測モデルではなく**設定テーブル**。統計もデータの蓄積も要らない
- いますぐ実装できる。`自動作成設定` に曜日 × 標準医師数の欄を足すだけ
- 「なぜこの人数か」を完全に説明できる
- **医師数が入力されたら必ずそちらを優先する。**設定値はあくまで穴埋め

シフト確定前に着手したい、という当初の困りごとは**これでほぼ解ける**。
段階2以降に進まなくても価値がある。

### 段階2: 28日周期の再来予測（休日ローリング込み）

処方日数の分布から「N 日後に何人戻ってくるか」を積み上げる（畳み込み）。

```
ある日の来局見込み = Σ（d 日前の処方箋枚数 × その日に処方日数 d が占めた割合）
```

積み上げた日が休診日なら、営業日カレンダー（`祝日マスタ`）で前後へ寄せる。
**寄せる向きは決め打ちにせず、実績から当てる。**

**いまのデータでは計算できない。**日報アプリが持っているのは
`処方箋枚数`（件数）だけで、**処方日数の内訳が無い**。
段階2に進むなら、日報アプリ側に「処方日数別の枚数」または
「平均処方日数」を記録する項目を足す必要がある。★別プロジェクトへの依存

残薬日数まで見るなら、さらに記録項目が要る。段階を分ける理由はここ。

### 段階3: 蓄積したデータでモデルを育てる

日報の記録が貯まってから。曜日・祝日前後・月初月末・季節性を足していく。

**説明できる形に留めること。**この出力は人の休みを決める。
「なぜこの日は3人なのか」を答えられない仕組みは労務に乗らない。
係数の見える回帰までにして、ブラックボックスには踏み込まない。

## 5. カセット式の差し替え

モデルが無くても動き、あとから差し込める形にする。

### 5.1 出力の単位を揃える ★これが成立の条件

各段が返すのは **`required`（必要人数）** に統一する。
単位が混ざると合成も比較もできない。

- モデルが出すのは「来局見込み」→ そこから `required` へ変換して返す
- 医師数の経路だけが `医師数 + n` で `required` を作る
- 設定表は `required` を直接持つ

**「医師数相当」に揃えてはいけない。** §2 のとおり医師数は粗い信号なので、
そこへ一度落とすと、モデルの解像度をわざわざ捨てることになる。

### 5.2 序列（日ごとに評価する）

月単位ではなく**日ごと**に決める。
「医師数が一部の日だけ入力済み」が最も普通の状態だから。

```
1. 実績              … 過ぎた日。予測を当てない
2. 医師数（確定）    … 人が確定と印を付けたもの
3. モデル            … 「使える」と自己申告したときだけ
4. 医師数（暫定）    … 確定前の見込み値
5. 設定表            … 休診日 / 祝日 / 曜日 を1枚で引く
6. 既定値            … Config の固定値
─────────────────────────
   下限・上限でクリップ
   その日の根拠を記録する
```

**祝日は曜日より先に見る。**祝日は曜日を上書きする性質なので、
「曜日 → 祝日」の順だと祝日が効かない。
そもそも休診日・祝日・曜日は排他の段ではなく**1枚の表**にまとめられる。
段を減らしたほうが説明も楽になる。

### 5.3 決めきれていないこと

**モデル（3）と暫定の医師数（4）はどちらが上か。**
ここではモデルを上に置いた。暫定値は人の当て推量で根拠が残らないため。
逆の考え方もありうる。実際に運用してみないと決められない。

### 5.4 見落としやすい点

| | |
|---|---|
| **クリニックの休診日 ≠ 国民の祝日** | 年末年始・お盆・学会・臨時休診は `祝日マスタ` に無い。**別の概念が要る** |
| **空欄が2つの意味を持つ** | 「未入力」と「その日は休診（0診）」が区別できない。フォールバックすると休診日に5診を当てる |
| **暫定と確定の区別が無い** | 確定前に着手するなら、医師数欄が見込みで埋まっていることがある |
| **モデルは有無の二値ではない** | データ不足の期間は「動くが当たらない」。値だけでなく**使えるかどうか**を返す必要がある |
| **下限・上限が無い** | どの経路から来ても 0 や負や現実離れした値になりうる。開局に要る最低薬剤師数は下限として要る |
| **根拠が残らないと説明できない** | 日ごとに供給元が変わるので、**何を根拠にしたかを日ごとに持ち、レポートに出す** |
| **検証を壊す** | チェーンが自動でモデルへ落ちると突き合わせができない。**固定式に戻すスイッチ**が要る |

## 6. モデルの形 — 表を運用に、回帰を分析に

**いまの式もすでに回帰である。**

```
required = 医師数 + n     ←  傾き 1、切片 n の1変数線形モデル
```

「改良」とはパラダイムの変更ではなく、**係数を動かし変数を増やす**こと。

### 6.1 5〜6人の職場では出力の幅が狭い

`required` が現実に取る値は 3〜6 程度。回帰が 4.3 と出しても 4 に丸める。
**求められるのは精度ではなく、どこで 4 から 5 に切り替わるかという境界だけ。**

帰結が2つある。

1. 小数点以下を当てにいく労力は捨てになる
2. `曜日 × 医師数 → 必要人数` の表（7 × 4 = 28 マス程度）で足りる

### 6.2 表と回帰

| | 表 | 回帰 |
|---|---|---|
| 説明 | セルを見れば分かる | 係数を読む必要がある |
| 修正 | 担当者がその場で直せる | 再学習が要る |
| データ量 | 要らない | 変数を増やすほど要る |
| 未知の組合せ | 埋められない | 外挿する（危ういが） |

労務に使うものなので、**担当者が「月曜の5診は4人」と自分で直せる**ことの価値が大きい。

### 6.3 結論

**回帰は分析に、表を運用に。**

1. データが貯まったら回帰で「どの要素が効くか」を調べる（分析）
2. その結論を表に焼く（運用）
3. 表は担当者が見て直せる

「28日周期が効く」「祝日明けは重い」といった発見は回帰から出てくるが、
**発見を表に落としてから使う**。本番に回帰そのものを置かない。

## 7. 個人の戦力を点数にしない ★決定

人によって処理できる量は違う。派遣薬剤師は調剤はある程度できるが締め作業はできない。
技術的には「投薬戦力指数」「調剤速度指数」のような重みを持たせられる。

**やらない。**

### 7.1 理由1: 点数は現場の反感を買う

共有のスプレッドシートに「この人は 0.6」と並ぶのは、**人事評価が表に出ている**のと同じ。

興味深いことに、**能力に関わる情報はすでに表に出ていて、問題になっていない**。

```
遅番・遅半 可否 = 不可      ← 受け入れられている
調剤速度指数 = 0.6          ← 反感を買う
```

情報量は近いのに受け取られ方が違う。前者は**事情**に読めるからだろう。
「保育園の迎えがある」「契約の範囲」。後者は**評価**にしか読めない。

**指針: 能力は「条件」の形で表し、「点数」の形にしない。**

### 7.2 理由2: 隠すと説明できなくなる

この道具は「なぜこの日はこの人数か」を説明できる必要がある（§4 段階3）。

戦力を数値で持つと、**隠すか説明するかのどちらかを諦めることになる**。
レポートに「必要3人に対して戦力換算 2.1」と書けば数値が露出し、
書かなければ「なぜこの日だけ4人か」に答えられない。

**数値を持たない、という選択はこの矛盾自体を消す。**

### 7.3 理由3: 保守が実利を上回る

6人 × 3指標 = 18個の数値を誰かが決めて保守することになる。
根拠になるデータは無い。設定の手間が効果を上回る。

### 7.4 代わりにやること

**「できない」だけをフラグで表す。**

| 表したいこと | やり方 | エンジンへの影響 |
|---|---|---|
| 調剤ができない | `区分` を分ける | 無し（既存の仕組み） |
| 締め作業ができない | `締め作業 可否` の欄を足す | 無し。レポートの警告から始める |
| どのくらい速いか | **表さない** | — |

これにより次が不要になった。

- 重み付き `cov`（エンジンの中核に手を入れる変更）
- `CoverBalance` の高速化の式（`score - (2d - 1)`）の作り直し
- 移植の検証を待つ必要

### 7.5 締め作業について残っている確認

実物では**派遣の欄にも ▲（遅番）が入っている**。
つまり「遅番には入るが締め作業はできない」なら、既存の `遅番・遅半 可否` では表せない。

```
いまある : その日の ▲ が lateMin 人以上いるか
足りない : その日の出勤者に、締められる人が1人以上いるか
```

これは VBA 版に無い形の制約。ただし段階を分けられる。

| 段階 | 内容 | エンジン変更 |
|---|---|---|
| **0** | レポートで警告するだけ「この日は締められる人がいません」 | **なし。移植中でも安全** |
| 1 | 配置の制約にする（自動で1人確保する） | あり。検証後 |

5〜6人の職場なら、警告さえ出れば手で直すほうが早い場面も多い。

### 7.6 あとから蒸し返さないために

**技術的には「重み付けすれば精度が上がる」は正しく見える。**
だからこそ、やらない理由を残しておく。
上の3つの理由（反感・説明との矛盾・保守コスト）が変わらない限り、この判断は変えない。

## 8. 移植の検証との関係 ★重要

移植の正しさは「**同じ入力なら VBA と同じ出力**」で確かめる（仕様書 §9 フェーズ3）。

`required` を予測値にすると、**定義上その検証はできなくなる**。
だから順序を守る。

1. 医師数から `required` を作る形で移植を終え、VBA 版と突き合わせる
2. **検証が済んでから**、`required` の作り方に選択肢を足す
3. 予測を使うときも、医師数が入力されている日は必ず医師数を優先する

**ただし「医師数に戻す」とは書かない。**§2 のとおり医師数も完全な指標ではない。
移植の検証中に固定式を使うのは **VBA と条件を揃えるため**であって、
医師数が正しいからではない。ここを混同すると、
検証が終わったあとも粗い式のまま運用してしまう。

## 必要人数の因果（現場からの指摘・2026-09-05）

必要人数の決まり方は、次の向きに流れる。

```
潜在患者数 → 予約数 → 医師数 → （薬剤師の必要人数）
```

**医師数は原因ではなく結果として現れる指標。** だから「医師1人あたり薬剤師 N 人」の
掛け算では人数が出ない。実際に絡む要素は次のとおり。

- 曜日（来局の波）
- 医師数
- 天候
- 予約数
- 祝日と土日のローリング

### 上限は需要では決まらない

**人数の上限は店舗の広さ（作業台の数）が先に来る。** 需要がいくらあっても、
物理的に入れる人数を超えられない。したがって上限は需要側のマスタではなく
**店舗マスタの属性**として持つ（`capPharm` / `capClerk`）。

### 下限が要る理由

少なすぎると調剤・鑑査・投薬が固定化して疲弊する。業務を回すための最低人数は
需要と別に要る。

### いまの実装（仮）

| | 置き場所 | 位置づけ |
|---|---|---|
| 下限・目安 | 必要人数マスタ（医師数ごと）＋ 店舗営業マスタ（曜日別下限）の大きいほう | **予測モデルまでの当て板** |
| 上限 | 店舗マスタの収容上限 | 物理的制約。モデルができても変わらない |

予測モデルができたら、置き換わるのは**下限・目安のほうだけ**。上限は残る。

### 分析時の注意

`prototype/samples/doctor-shift-*.json` の医師出勤表は**こちらで作った架空のデータ**。
